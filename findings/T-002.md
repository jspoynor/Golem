## 1 · Skill invocation names — SPEC §4

**Confirmed (doc + observed).** Plugin skills are *always* namespaced as
`/<plugin-name>:<skill-name>`. The namespace is the `name` field in
`.claude-plugin/plugin.json`; the skill name is the directory name under `skills/`.

Probe: plugin `golemprobe` with `skills/ping/SKILL.md`.

| Invocation | Result |
|---|---|
| `/golemprobe:ping` | ran, returned `PONG` |
| `/ping` | `Unknown command: /ping` |

The un-namespaced form does not exist. With `name: "golem"` in `plugin.json` and the
§1.4 directory layout, the six §4 skills resolve to exactly:

```
/golem:init
/golem:spec
/golem:plan
/golem:run
/golem:resume
/golem:status
```

**No collision risk with built-ins.** Because plugin skills only ever exist under the
namespace, `/golem:init` and `/golem:run` do not shadow or conflict with Claude Code's
own `/init` or any built-in. Docs state this explicitly: the original `/skill-name` and
the plugin copy both remain available rather than one overriding the other.

Two caveats worth recording:

- The frontmatter `name` field overrides the directory name **only** in the
  single-`SKILL.md`-at-plugin-root layout, or when a `skills` manifest entry points at a
  directory containing `SKILL.md` directly. In the normal `skills/<name>/SKILL.md`
  layout Golem uses (§1.4), the **directory name wins**. Naming the directories `init`,
  `spec`, `plan`, `run`, `resume`, `status` is what produces the strings above.
- `disable-model-invocation: true` in a skill's frontmatter makes it user-invoked only.
  Relevant to §1.3 ("inert by default"): without it, the model may auto-invoke a skill
  from task context. Not decided here — flagging it for whoever implements §4.

Docs: https://code.claude.com/docs/en/plugins ·
https://code.claude.com/docs/en/plugins-reference#skills

## 2 · The subagent-completion hook event — SPEC §8.1

### 2.1 The event exists and fires reliably

**Confirmed (observed).** The event is **`SubagentStop`**, "fired when a subagent
finishes." It fires from a plugin's `hooks/hooks.json`, receives JSON on stdin, and
supports a `matcher` on **agent type**.

`SubagentStart` also exists (fires on spawn, no blocking control) and is the natural
place to stage per-node state if T-014 needs it.

### 2.2 Actual observed `SubagentStop` input schema

Captured verbatim from a real run (keys only, values elided):

```
session_id              string
transcript_path         string   — main session transcript
cwd                     string
prompt_id               string   — UUID of the user prompt being processed
permission_mode         string   — e.g. "acceptEdits"
agent_id                string   — e.g. "ac35dfb60b68d30fe"
agent_type              string   — e.g. "Explore"; plugin-scoped as "golem:reviewer"
effort                  object   — { "level": "medium" }
hook_event_name         "SubagentStop"
stop_hook_active        boolean  — true when re-fired after a previous exit-2 block
agent_transcript_path   string   — .../subagents/agent-<agent_id>.jsonl
last_assistant_message  string   — the subagent's full final message text
background_tasks        array
session_crons           array
```

Four of these — `stop_hook_active`, `agent_transcript_path`, `background_tasks`,
`session_crons` — are **not in the published schema** but were present in every payload.
`agent_transcript_path` is useful (the subagent's own transcript, separate from the main
one); the undocumented ones should not be treated as load-bearing.

`SubagentStart` payload is the same minus `permission_mode`, `effort`,
`last_assistant_message`, and the stop-specific fields.

### 2.3 Matcher

**Confirmed (doc), partially observed.** `SubagentStop` matches on agent type, same
value set as `SubagentStart`: built-ins (`Explore`, `Plan`, `general-purpose`), custom
agent frontmatter `name`s, and plugin-scoped anchored forms like
`^golem:implementer-light$`. Observed working with a plain `Explore` matcher and with
`*`. The plugin-scoped form is doc-confirmed only — Golem has no agents yet (T-013), so
it is **untested** and should be re-verified in T-014.

Note the scoping rule: for a plugin agent, `agent_type` is the **plugin-scoped
identifier** (`golem:reviewer`), not the bare frontmatter name. A matcher written
against the bare name will silently never fire.

### 2.4 Hook config shape

```json
{
  "hooks": {
    "SubagentStop": [
      {
        "matcher": "^golem:implementer-light$",
        "hooks": [
          { "type": "command",
            "command": "\"${CLAUDE_PLUGIN_ROOT}\"/hooks/gate.sh",
            "timeout": 600 }
        ]
      }
    ]
  }
}
```

`${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_PLUGIN_DATA}` all substitute
into `command` and `args` and are exported as env vars. Default timeout is 600s, which
comfortably covers a `config.verify` run. Using `args` spawns the executable directly
with no shell.

## 3 · BLOCKING FINDING — `SubagentStop` cannot fail a node as §8.1 assumes

This is the load-bearing mechanism, so it was tested rather than assumed. **It does not
behave the way §8.1 describes.**

§8.1 says: *"Runs `config.verify` plus any node-level `verify` override. Exit 0 or the
node fails."* There is no exit code that fails a node.

### 3.1 What exit 2 actually does

**Confirmed (observed).** Exit 2 **blocks the subagent from stopping** and feeds stderr
back **to the subagent** as an error. The subagent gets another turn and keeps working.
It does not fail, and the orchestrator is never told anything.

Probe A — gate fails once, then passes:

- Hook exit 2 with stderr `"GOLEM GATE: verify command failed (exit 1)."`
- The subagent did not fail. It **argued with the gate**, concluded the message was
  spurious, and continued.
- The orchestrator's final report was a *narration of the gate message* — exactly the
  "orchestrator as judge" failure §7.2 exists to prevent.

Probe B — gate fails unconditionally:

- The hook fired **10 times** (an internal ceiling), `stop_hook_active` flipping to
  `true` after the first.
- The subagent then **stopped anyway** and returned success.
- The orchestrator reported **"The subagent succeeded"**, with the gate's failure text
  demoted to "noise, not a report of failure."

A permanently-failing verify command therefore produces: ~10 wasted subagent turns, a
polluted writeup, and a **passing** node. That is worse than no gate — it is §4.1's
"looks like a gate but isn't," one layer up.

### 3.2 The gate's verdict is invisible to the orchestrator

**Confirmed (observed, twice).** `hookSpecificOutput.additionalContext` on
`SubagentStop` is delivered **to the subagent**, not to the main thread.

Probe C — hook emitted `additionalContext` containing the sentinel
`GOLEM_GATE_RESULT: verdict=fail ...`, then the orchestrator was asked to quote any text
containing that string. Both runs: **NOTSEEN**. In one run the subagent visibly reacted
to it ("Gate unchanged."), proving delivery — to the wrong party.

So the hook can observe the node, and can run `config.verify`, but has **no return path
to the orchestrator at all**.

### 3.3 What this means for T-003 and T-014

TASKS.md T-014 says: *"If T-002 found no suitable event, stop and raise it rather than
substituting a prompt."* Raising it here. The finding is narrower than "no suitable
event" — the event exists and is well-instrumented — but the two properties §8.1
depends on are both absent:

1. no exit code that marks a node failed;
2. no channel from hook to orchestrator.

**T-003 must resolve this before T-014.** The design intent of §8.1 — *judgment by a
deterministic component, not by the agent that wants to succeed* — is still reachable,
but not through the hook's return value. The obvious route is a **side channel**: the
`SubagentStop` hook runs `config.verify` and writes a result file (e.g.
`.golem/runs/<id>/gate-<node>.json` with exit code and captured output), and the
orchestrator **reads that file** after the Task returns. The hook remains the judge, the
orchestrator remains a router reading a fact off disk, and §7.2 and §8.1's intent both
survive. `agent_id` and `agent_type` are in the payload to key the file by node.

That is a design change to §8.1's mechanics, not to its principle, so it belongs in
T-003's reconciliation — not here. I am not amending SPEC.md under T-002.

Docs: https://code.claude.com/docs/en/hooks#subagentstop
